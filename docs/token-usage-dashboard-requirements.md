# Token 用量看板需求文档

## 1. 文档目的

本文档定义 `ESP32 + 4.2 寸黑白红三色墨水屏` 的「Token 用量看板」界面需求、数据范围、显示约束与验收标准。

固件基于 **J-Calendar** (jcalendar-1.1.9) z21 环境，看板功能作为独立模块集成在固件中。主机端程序位于 `tools/token_dashboard_host/`。

## 2. 项目目标

构建一个适用于 `400x300`、`4:3` 比例三色墨水屏的 Token 用量监控界面，用于定时展示：

- 当日 Token 总量、输入、输出、缓存；
- `GLM CodingPlan` 套餐的 `5 小时` 与 `一周` 用量；
- `GPT Plus` 套餐的 `5 小时` 与 `一周` 用量；
- 模型维度的调用次数、Token 用量、占比；
- 上次刷新时间；
- 设备侧 Wi-Fi 状态与电量状态。

后续系统目标为：主机每 `5 分钟` 聚合一次数据，通过蓝牙将看板数据推送到 ESP32，再由设备刷新墨水屏展示。

## 3. 适用范围

### 3.1 本期纳入范围

- 墨水屏看板页面的唯一界面设计；
- 看板字段定义与显示口径；
- 主机侧数据采集范围与刷新节奏；
- ESP32 端看板展示与刷新触发；
- 主机到设备的 BLE 数据推送链路。

### 3.2 本期不纳入范围

- 多页面切换；
- 触摸交互、按钮交互、翻页；
- 历史趋势页；
- 阈值配置页；
- 屏幕上的手动刷新按钮；
- 自定义主题或换肤；
- 除看板之外的其他可视化内容。

## 4. 硬件与运行环境要求

### 4.1 设备要求

- 主控：ESP32 开发板；
- 屏幕：4.2 寸黑白红三色墨水屏；
- 分辨率：`400 x 300`；
- 屏幕方向：横屏；
- 显示比例：`4:3`。

### 4.2 刷新方式要求

- 数据采集周期：`5 分钟`；
- BLE 推送周期：`5 分钟`；
- 墨水屏在收到完整的新看板数据后刷新；
- 单次刷新以完整看板为单位，不拆分局部区域独立更新。

## 5. 界面显示总要求

### 5.1 颜色限制

界面颜色严格限制为以下三种：

- 白色：背景；
- 黑色：文字、边框、分隔线、普通进度条；
- 红色：达到告警阈值的套餐用量进度条和百分比。

禁止使用：

- 灰色；
- 渐变；
- 半透明；
- 橙色、蓝色、绿色、紫色等任何其他颜色。

### 5.2 风格要求

- 简洁；
- 规整；
- 信息密度适中；
- 适合墨水屏显示；
- 避免复杂图标、阴影、装饰图案；
- 所有信息必须围绕看板主体内容组织，不增加无关视觉元素。

### 5.3 布局总要求

界面自上而下固定分为 `5` 个区域：

1. 顶部标题栏；
2. 今日 Token 用量概览区；
3. 两个套餐用量进度区；
4. 模型用量表格区；
5. 底部刷新时间区。

所有区域必须使用黑色细边框或分隔线组织；整体保持对齐、留白均衡。

## 6. 顶部标题栏需求

### 6.1 左侧内容

- 标题：`Token 用量看板`

### 6.2 右侧内容

- `Wi-Fi 已连接`
- 电量图标
- 电量百分比，例如：`87%`

### 6.3 明确禁止

- 不显示当前时间；
- 不显示日期；
- 不显示设备名称；
- 不显示网络名称；
- 不显示其他状态提示。

## 7. 今日 Token 用量概览区需求

### 7.1 区域结构

该区域横向分为 `4` 列：

1. 今日总量；
2. 输入；
3. 输出；
4. 缓存。

### 7.2 字段定义

#### 今日总量

- 标题：`今日总量`
- 示例值：`71.5M`
- 单位：`TOKEN`

#### 输入

- 标题：`输入`
- 示例值：`24.8M`

#### 输出

- 标题：`输出`
- 示例值：`39.2M`

#### 缓存

- 标题：`缓存`
- 示例值：`7.5M`

### 7.3 显示要求

- `今日总量` 的数值字号必须最大；
- `输入 / 输出 / 缓存` 三列保持相同字号和布局；
- 列与列之间使用竖向虚线或细分隔线；
- `今日总量` 下方显示单位 `TOKEN`；
- 不允许增加其他统计字段。

### 7.4 明确禁止

- 不显示今日占比；
- 不显示近 5 小时；
- 不显示本周累计；
- 不显示图标；
- 不显示任何额外说明文字。

## 8. 套餐用量进度区需求

### 8.1 区域结构

该区域为左右两列：

- 左侧：`GLM CodingPlan 套餐`
- 右侧：`GPT Plus 套餐`

### 8.2 每个套餐卡片的固定内容

每个套餐卡片内部必须固定展示两行：

- 第一行：`5 小时`
- 第二行：`一周`

每一行从左到右固定展示：

1. 时间范围标题；
2. 横向进度条；
3. 百分比；
4. 刷新时间或重置时间。

### 8.3 示例

#### GLM CodingPlan 套餐

- `5 小时    [进度条]    82%    22:17`
- `一周      [进度条]    64%    5月31日`

#### GPT Plus 套餐

- `5 小时    [进度条]    43%    22:17`
- `一周      [进度条]    57%    5月31日`

### 8.4 显示要求

- 两行必须严格上下对齐；
- 两行进度条的起始位置、宽度、百分比位置、时间位置完全一致；
- 两行之间可使用黑色虚线轻量分隔；
- 只显示百分比；
- GLM 与 GPT 都必须同时展示 `5 小时` 和 `一周` 两项；
- 任一套餐不得缺项。

### 8.5 明确禁止

- 不显示类似 `16.4M / 20M` 的额度值；
- 不显示类似 `128M / 200M` 的额度值；
- 不显示其他时间窗口；
- 不显示其他描述文字。

## 9. 套餐进度条告警规则

### 9.1 颜色规则

- 用量 `< 80%`：进度条黑色填充，百分比黑色文字；
- 用量 `>= 80%`：进度条红色填充，百分比红色文字。

### 9.2 告警范围

- 仅对达到阈值的套餐项使用红色；
- 其他普通内容必须保持黑色。

### 9.3 示例

- `GLM CodingPlan` 的 `5 小时 82%` 使用红色；
- 其他套餐项保持黑色。

## 10. 模型用量表格区需求

### 10.1 区域结构

直接显示表格，不增加标题和说明文字。

### 10.2 表格字段

从左到右固定为：

- 模型
- 提供商
- 调用
- TOKEN
- 占比

### 10.3 示例数据

| 模型 | 提供商 | 调用 | TOKEN | 占比 |
|---|---|---:|---:|---|
| glm-4.7 | zhipu | 454 | 32.0M | 45.2% |
| glm-5.1 | zhipu | 427 | 39.5M | 42.5% |
| gpt-5.3-codex | openai | 106 | 22.0M | 10.6% |
| glm-4.5-air | zhipu | 16 | 1.5M | 1.6% |
| gpt-5.5 | openai | 1 | 55.4K | 0.1% |

### 10.4 显示要求

- 每一行使用横向细线分隔；
- 列宽稳定；
- 文字左对齐或居中对齐，但整体必须整齐；
- `占比` 列必须同时显示小型横向进度条和百分比；
- `占比` 进度条默认黑色；
- 不增加排名、箭头、趋势、图标。

### 10.5 数据要求

- 模型行数据来源于当日数据；
- 默认展示当日 Token 总量前 `5` 的模型；
- 如不足 `5` 行，则按实际模型数展示。

## 11. 底部刷新时间区需求

### 11.1 显示内容

底部左侧仅显示：

- `上次刷新：09:24`

### 11.2 明确禁止

- 不显示 API 拉取状态；
- 不显示每 30 分钟刷新；
- 不显示下次刷新；
- 不显示图标；
- 不显示底部状态栏；
- 不显示其他提示文案。

## 12. 数据来源需求

### 12.1 今日 Token 数据

今日总量、输入、输出、缓存、模型表格数据，要求来源于本机 `aiusage` 数据。

需求口径如下：

- 时间范围：按主机本地自然日统计；
- `今日总量 = 输入 + 输出 + 缓存 + 其他 aiusage 计入 total 的 token 字段`;
- `输入` 来自 `input_tokens`；
- `输出` 来自 `output_tokens`；
- `缓存` 优先来自 `cache_read_tokens`；
- 模型表格按 `模型 + 提供商` 聚合。

### 12.2 GLM 套餐数据

`GLM CodingPlan` 套餐需展示：

- 5 小时使用百分比；
- 5 小时刷新/重置时间；
- 一周使用百分比；
- 一周刷新/重置时间。

数据来源调整为 `智谱开放平台套餐用量接口`。

接口信息：

- Method：`GET`
- URL：`https://open.bigmodel.cn/api/monitor/usage/quota/limit`
- Header：`Authorization: Bearer <GLM_API_KEY>`

当前已验证该接口可以正常返回 `code=200` 的真实数据。

说明：

- 返回体为 `data.limits[]` 数组；
- 当前已确认能返回 `percentage`、`nextResetTime`、`usage`、`currentValue`、`remaining` 等字段；
- 当前映射规则固定如下：
  - `type = TOKENS_LIMIT` 且 `unit = 3`：映射为界面的 `5 小时`
  - `type = TOKENS_LIMIT` 且 `unit = 6`：映射为界面的 `一周`
  - `type = TIME_LIMIT` 且 `unit = 5`：表示 `MCP 每月额度`，本期不在看板展示
- `5 小时` 项当前无 `nextResetTime` 时，仅展示百分比，重置时间显示规则由实现阶段按固定文案处理。

### 12.3 GPT 套餐数据

`GPT Plus` 套餐需展示：

- 5 小时使用百分比；
- 5 小时刷新/重置时间；
- 一周使用百分比；
- 一周刷新/重置时间。

数据来源调整为当前 Codex 本地会话日志中的 `rate_limits` 数据。

当前已确认：

- Codex 本地会话文件会持续写入 `rate_limits.primary` 与 `rate_limits.secondary`；
- `primary.window_minutes = 300`，可直接映射为 `5 小时`；
- `secondary.window_minutes = 10080`，可直接映射为 `一周`；
- 两者均包含：
  - `used_percent`
  - `resets_at`
  - `plan_type`

因此本期不再将 GPT 套餐数据依赖于额外远程接口，默认从本机 Codex 会话日志读取。

## 13. 刷新与推送需求

### 13.1 主机侧刷新

- 每 `5 分钟` 触发一次采集；
- 采集后生成完整看板数据；
- 生成成功后通过 BLE 推送至 ESP32。

### 13.2 设备侧刷新

- ESP32 在收到完整有效数据后刷新屏幕；
- 刷新内容必须为整页看板；
- 不允许刷新成中间态或半成品页面。

## 14. 排版与视觉规范

- 白底黑字；
- 红色仅用于超过 `80%` 的套餐告警项；
- 标题字号最大；
- 今日总量数值次突出；
- 表格与套餐百分比层级清晰；
- 进度条使用空心黑色边框；
- 内部按比例填充黑色或红色；
- 可使用轻微圆角；
- 不使用阴影、渐变、彩色背景、复杂插图。

## 15. 严格禁止事项

- 顶部右侧显示当前时间；
- 增加今日占比、近 5 小时、本周累计等概览字段；
- 增加“模型排行”标题；
- 增加 API 拉取状态、下次刷新、刷新频率；
- 展示套餐具体 Token 配额数字；
- 使用黑白红之外的颜色；
- 增加图标、图表、趋势、按钮、状态提示或说明文字；
- 改变既定布局层级。

## 16. 验收标准

### 16.1 界面验收

- 画面严格分为 `5` 个区域；
- 标题栏右侧不显示时间；
- 今日概览区只有 `4` 列且字段完整；
- 套餐区左右两卡片均包含 `5 小时` 与 `一周`；
- 模型表格字段顺序必须一致；
- 底部仅显示 `上次刷新`。

### 16.2 视觉验收

- 全屏仅出现黑、白、红三色；
- 红色仅出现在 `>= 80%` 的套餐项；
- 没有阴影、渐变、背景色块和额外图标；
- 分隔线清晰；
- 文字在墨水屏上可读。

### 16.3 数据验收

- 今日数据来自 `aiusage`；
- 模型表格与今日数据口径一致；
- GLM 套餐和 GPT 套餐均展示两档时间窗口；
- 上次刷新时间反映最后一次成功推送时间。
