# Token 用量看板刷新优化方案

## 结论

原文方向总体合理，但有两个需要修正的点：

1. 压缩传输方案可行，但不是"只改 Python 端"。
2. 跳过无变化帧应该放到 BLE 连接前，否则仍会浪费扫描、连接和状态读取时间。

另外，当前实现里还漏掉了一个最直接的 P0 优化：主机端在黑色平面发送完后固定等待 `5s`，这段等待目前看是主机侧人为加入的，不是固件协议硬要求。

## 基于当前代码的现状

当前刷新链路来自：

- `tools/token_dashboard_host/main.py`
- `tools/token_dashboard_host/ble/transport.py`

实际流程是：

1. 采集数据
2. 连接设备并读取 `READ_MSD`
3. 渲染 `400x300` 看板
4. 转成黑/红双平面位图
5. 通过 BLE 发送整帧
6. 触发三色墨水屏全刷

### 当前主要耗时点

| 阶段 | 耗时 | 说明 |
|------|------|------|
| BLE 传 PLANE_0 (15KB) | ~5s | 500 字节分块 + 每块等 ACK |
| 主机端固定等待 | **5s** | `send_3color_image()` 里写死的 `await asyncio.sleep(5)` |
| BLE 传 PLANE_1 (15KB) | ~35s | 同样按 chunk 串行发送，红色平面更慢 |
| 屏幕物理刷新 | ~12-15s | 三色墨水屏全刷固有时延 |
| **总计** | **~57-60s** | 还未计入 BLE 扫描/连接开销 |

### 原文里遗漏的关键信息

#### 1. 固件渲染模式已经实现

当前固件（`jcalendar-1.1.9/src/`）已实现 `0x0078/0x0079/0x007A` 结构化快照协议，Host 端切换到 `firmware_render` 模式即可将传输从 ~30KB 降到 192B。

#### 2. "跳过无变化帧"应前移到 BLE 连接前

当前 `run_cycle()` 先连接设备再渲染和发送。更合理的做法是先对"本次要展示的数据"做摘要比较，无变化就整轮跳过。

#### 3. 主机端固定 5 秒等待可以直接删除

`send_3color_image()` 里黑平面发完后固定 `sleep(5)` 没有协议约束，可以直接去掉。

## 优化方案

### 方案 1：删除主机端固定 5 秒等待（P0）

直接去掉 `send_3color_image()` 里黑色平面后的固定等待。

- 不改协议
- 不改固件
- 只改主机端几行代码
- **预期收益**：每次刷新固定减少约 `5s`

### 方案 2：连接前跳过无变化周期（P0）

缓存上一次业务数据摘要，本轮先比较，完全一致则不连接 BLE、不渲染、不发送。

- **预期收益**：无变化周期直接跳过整轮刷新
- **改动范围**：`main.py` 小改

### 方案 3：使用 firmware_render 模式（P1）

切换到结构化快照模式（已有实现），传输从 ~30KB 降到 192B。

- **预期收益**：BLE 传输从 ~40s 降到 <1s
- **改动范围**：`config.py` 配置切换，无需改代码

### 方案 4：复用 BLE 连接（P2）

保留连接到下一轮，失败时再重连。

- **预期收益**：节省每轮扫描/重连时间
- **改动范围**：主机端小改

### 方案 5：局部刷新（P3）

当前看板是三色整屏设计，局部刷新方案更适合后续黑白局部刷新场景。

### 方案 6：WiFi 传输替代 BLE（P4）

传输可从 ~40s 压到 <1s，但总耗时仍受 12-15s 物理刷新限制。

## 调整后的优先级

| 优先级 | 方案 | 预期收益 | 开发量 |
|--------|------|----------|--------|
| P0 | 删除固定 5s 等待 | 每次 `-5s` | 极小 |
| P0 | 连接前跳过无变化 | 无变化时 `0s` | 小 |
| P1 | firmware_render 模式 | 传输从 ~40s 降到 <1s | 配置切换 |
| P2 | 复用 BLE 连接 | 节省连接时间 | 小 |
| P3 | 局部刷新 | 特定场景极快 | 中 |
| P4 | WiFi 传输 | 传输趋近 0s | 中 |

## 推荐落地顺序

1. 删除主机端固定 `5s` 等待
2. 把"无变化跳过"前移到 BLE 连接前
3. 切换到 `firmware_render` 模式
