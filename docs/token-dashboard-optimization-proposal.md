# Token 用量看板刷新优化方案

## 结论

原文方向总体合理，但有两个需要修正的点：

1. 压缩传输方案可行，但不是“只改 Python 端”。
2. 跳过无变化帧应该放到 BLE 连接前，否则仍会浪费扫描、连接和状态读取时间。

另外，当前实现里还漏掉了一个最直接的 P0 优化：主机端在黑色平面发送完后固定等待 `5s`，这段等待目前看是主机侧人为加入的，不是固件协议硬要求。

## 基于当前代码的现状

当前刷新链路来自：

- `tools/token_dashboard_host/main.py`
- `tools/token_dashboard_host/ble/transport.py`

实际流程是：

1. 采集数据
2. 连接设备并读取 `READ_MSD`
3. 渲染 `400x300` 看板
4. 转成黑/红双平面位图
5. 通过 BLE 发送整帧
6. 触发三色墨水屏全刷

### 当前主要耗时点

| 阶段 | 耗时 | 说明 |
|------|------|------|
| BLE 传 PLANE_0 (15KB) | ~5s | 500 字节分块 + 每块等 ACK |
| 主机端固定等待 | **5s** | `send_3color_image()` 里写死的 `await asyncio.sleep(5)` |
| BLE 传 PLANE_1 (15KB) | ~35s | 同样按 chunk 串行发送，红色平面更慢 |
| 屏幕物理刷新 | ~12-15s | 三色墨水屏全刷固有时延 |
| **总计** | **~57-60s** | 还未计入 BLE 扫描/连接开销 |

### 原文里遗漏的关键信息

#### 1. 压缩能力在固件端已存在，但当前默认配置未必可直接用

固件端已经支持压缩直写：

- `src/display_service.cpp` 的 `handleDirectWriteStart()`
- `src/display_service.cpp` 的 `handleDirectWriteCompressedData()`

但压缩接收容量受 `display.transmission_modes` 控制，当前 `esp32-N4` 内置默认配置里：

- `src/config_parser.cpp` 把 `display.transmission_modes` 设成了 `0`

这意味着压缩方案要成立，至少要同时满足下面两件事：

1. 主机端按压缩协议发送
2. 设备侧配置打开 `TRANSMISSION_MODE_ZIP`

所以“压缩传输”不是纯 Python 改动。

#### 2. “跳过无变化帧”现在写在文档里没错，但落点应该前移

当前 `run_cycle()` 的顺序是先连接设备，再渲染和发送。

如果只是“渲染完后比较位图，不同才推送”，那虽然能省掉 BLE 大图传输和屏幕刷新，但仍然会消耗：

- BLE 扫描/连接
- `READ_MSD` 往返
- 一次完整渲染

更合理的做法是先对“本次要展示的数据”做摘要比较，无变化就整轮跳过。

#### 3. 当前最容易拿到的收益，其实是删掉主机端固定 5 秒等待

`tools/token_dashboard_host/ble/transport.py` 里当前逻辑是：

1. 黑色平面发送完
2. 收到固件 `0x72`
3. 仍然固定 `sleep(5)`
4. 再开始发送红色平面

而固件 `handleDirectWriteEnd()` 在双平面切换时已经直接回 ACK，并没有看到额外要求主机必须再等 5 秒的协议约束。这个等待很可能是为了“保险”加上的经验值，但它每次都会真实增加总耗时。

## 调整后的优化方案

### 方案 1：删除主机端固定 5 秒等待

直接去掉 `send_3color_image()` 里黑色平面后的固定 `sleep(5)`，改为收到切平面 ACK 后立即发送红色平面。

- 不改协议
- 不改固件
- 只改主机端几行代码
- **预期收益**：每次刷新固定减少约 `5s`

这是当前最应该优先做的 P0。

### 方案 2：连接前跳过无变化周期

在主机端缓存上一次“展示数据摘要”或“最终双平面摘要”，本轮先比较，完全一致则不连接 BLE、不读状态、不渲染、不发送。

建议优先比较业务数据摘要，而不是比较整张位图：

- 数据摘要更轻
- 可以在连接前完成判断
- 真正做到无变化时 `0s`

如果必须把电量/WiFi 状态也展示在屏幕上，就把这些设备状态字段也纳入摘要即可。

- **预期收益**：无变化周期直接跳过整轮刷新
- **改动范围**：`main.py` 小改

### 方案 3：启用 ZIP 压缩传输

主机端发送压缩后的双平面数据，`DIRECT_WRITE_START` 携带 4 字节解压后总长度，设备端用现有 zlib 流程解压。

看板画面以白底、文字、细线和少量红色元素为主，压缩率通常会比较高，这个方向仍然是最有价值的传输优化。

但这项方案要补齐两个前提：

1. 主机端按压缩协议封包
2. 设备配置里打开 `TRANSMISSION_MODE_ZIP`

- **预期收益**：30KB 双平面大概率可压到数 KB，传输时间从 `40s` 量级降到 `5-10s` 量级
- **改动范围**：主机端 + 设备配置/固件默认配置

这项方案应放在“删掉 5 秒等待”之后立即做。

### 方案 4：复用 BLE 连接

当前每轮都：

1. 扫描设备
2. 连接
3. 开启 notify
4. 发送完成后断开

如果设备供电稳定，可以把连接保留到下一轮，失败时再重连。

- **预期收益**：节省每轮扫描/重连时间
- **局限**：只能省连接开销，不能解决大图传输慢的问题
- **改动范围**：主机端小改

这项方案可以作为次一级优化，但优先级低于前 3 项。

### 方案 5：局部刷新

固件已有 `0x0076` 局部写入口，但当前约束比原文写得更硬：

- 依赖 `etag`，要求 `oldEtag == displayed_etag`
- 矩形 `x` 和 `width` 必须按 `8` 像素对齐
- 主要面向 `1bpp` 局部路径
- 当前看板是三色整屏设计，不适合作为第一阶段主方案

所以这个方向并不是“不能做”，而是更适合作为后续专门的黑白局部刷新方案，而不是当前这块三色整屏看板的近期解法。

- **预期收益**：特定黑白局部场景下非常快
- **局限**：不适合当前三色整屏主路径
- **改动范围**：主机端 + 协议细节适配

### 方案 6：WiFi 传输替代 BLE

这个方向仍然成立，但它解决的是“传输慢”，不解决“三色墨水屏全刷慢”。

- 传输可从 `40s` 压到 `<1s`
- 但总耗时仍受 `12-15s` 物理刷新限制
- 适合常供电、已有配网的场景

如果当前目标只是把“现在这版看板”尽快提速，优先级不如前 3 项。

### 方案 7：固件端渲染

这是长期方案，不适合当前阶段优先做。

- 传输最省
- 结构最彻底
- 但开发量最大，且会把布局、字体、表格渲染复杂度搬到固件端

## 调整后的优先级

| 优先级 | 方案 | 预期收益 | 开发量 |
|--------|------|----------|--------|
| P0 | 方案 1：删除主机端固定 5 秒等待 | 每次刷新固定 `-5s` | 极小（主机端几行） |
| P0 | 方案 2：连接前跳过无变化周期 | 无变化时整轮 `0s` | 小 |
| P1 | 方案 3：启用 ZIP 压缩传输 | 传输时间从 `40s` 量级降到 `5-10s` | 中（主机端 + 设备配置） |
| P2 | 方案 4：复用 BLE 连接 | 节省扫描/重连时间 | 小 |
| P3 | 方案 5：局部刷新 | 特定场景可极快 | 中 |
| P4 | 方案 6：WiFi 传输 | 传输趋近 `0s` | 中 |
| P5 | 方案 7：固件端渲染 | 传输最小 | 大 |

## 推荐落地顺序

建议按这一条线推进：

1. 先删除主机端固定 `5s` 等待
2. 再把“无变化跳过”前移到 BLE 连接前
3. 然后启用 ZIP 压缩传输

这样不用改整体架构，就能先拿到一轮确定性收益；其中前两项做完后，已经能明显改善“每次刷新都很慢”的体感，第三项再解决真正的传输瓶颈。

## 保留现有模式并新增固件端渲染

### 目标

本次改造采用一条明确路线：

1. 保留现有“主机渲染位图 + BLE 推图”模式，作为兼容模式继续存在
2. 新增“主机采集数据 + BLE 发送结构化快照 + 固件固定模板渲染”模式
3. 两种模式共用同一套数据采集逻辑，由主机侧通过配置选择发送路径

这个方案的核心不是替换现有位图模式，而是把“传输 30KB 双平面位图”改成“传输 200B 级别业务快照”，从而把 BLE 传输时间压到接近 `0s`。

### 为什么新增固件端渲染现在可做

当前固件虽然没有完整 UI 引擎，但已经具备三类可复用基础：

1. 已有稳定的 BLE 命令入口和 ACK 往返机制
2. 已有 Boot Screen 文本与像素绘制逻辑，可复用到固定模板渲染
3. 当前看板布局其实是固定模板，不需要通用排版引擎

因此不需要做“通用中文 UI 框架”，只需要做“固定模板 + 少量绘图原语 + 结构化数据解析”。

### 总体改造方式

#### 主机侧

主机仍然负责：

- 采集 `aiusage`
- 采集 GLM 套餐
- 采集 GPT 套餐
- 组装统一 `DashboardSnapshot`

区别只在发送阶段分成两条路径：

1. `bitmap` 模式
   - 继续走现有 `render_dashboard() -> rgb_to_bitplanes() -> send_3color_image()`
2. `firmware_render` 模式
   - 不再渲染 PIL 图片
   - 直接把 `DashboardSnapshot` 编码成二进制 payload
   - 通过新的 BLE 命令发给设备

#### 固件侧

固件新增一个“固定模板看板渲染器”，负责：

- 解析结构化 payload
- 在设备本地绘制固定文本、边框、分隔线、进度条、模型表格
- 本地读取并显示电量/Wi-Fi 状态
- 触发整屏刷新

### 建议的双模式结构

#### Host 侧结构

建议新增一个统一快照层：

```text
collectors -> DashboardSnapshot -> transport encoder
                                  |- bitmap encoder
                                  |- firmware-render encoder
```

建议主机侧只保留一份统一数据模型，不要为固件渲染再单独造第二套 collector。

#### 固件侧结构

建议固件新增 3 个职责清晰的模块：

1. `dashboard_protocol`
   - 负责新 BLE 命令的收包、分块、CRC 校验、版本检查
2. `dashboard_snapshot`
   - 负责把二进制 payload 解析为内存结构
3. `dashboard_renderer`
   - 负责固定模板绘制和最终刷新

### 建议的 BLE 命令设计

当前 `0x0070-0x0076` 已经被直接写图、局部刷新和设备控制占用。建议新增一组连续命令，不和现有位图链路混用：

| 命令 | 含义 |
|------|------|
| `0x0078` | `DASHBOARD_RENDER_START` |
| `0x0079` | `DASHBOARD_RENDER_DATA` |
| `0x007A` | `DASHBOARD_RENDER_COMMIT` |

建议响应：

| 响应 | 含义 |
|------|------|
| `[0x00, 0x78]` | START ACK |
| `[0x00, 0x79]` | DATA ACK |
| `[0x00, 0x7A]` | COMMIT ACK |
| `[0x00, 0x7B]` | 刷新成功 |
| `[0x00, 0x7C]` | 刷新超时 |
| `[0xFF, opcode, errorCode, 0x00]` | 协议错误 |

这样可以做到：

- 现有位图模式完全不受影响
- 新模式有独立协议状态机
- Host 端可以明确知道当前走的是哪条链路

### 建议的设备侧数据格式

这里建议不要用 JSON，直接用固定长度的二进制 `DashboardSnapshotV1`。

原因很直接：

- BLE 下更省字节
- 固件解析最简单
- 不需要额外 JSON 解析器
- payload 能稳定控制在 `200B` 左右

#### 编码约定

- 字节序：`little-endian`
- 文本编码：动态字符串仅允许 `ASCII`
- 模型条数固定最多 `4` 条，与当前实际页面一致
- 固定中文标签不从主机发送，由固件内置

#### Start 帧

`0x0078` 请求体：

```text
[version:1]
[flags:1]
[payload_len_le:2]
[crc32_le:4]
[optional_initial_payload...]
```

字段定义：

- `version`
  - 固定为 `1`
- `flags`
  - bit0: 请求使用 `FULL` 刷新
  - bit1: 请求使用 `FAST` 刷新
  - bit2-bit7: 预留
- `payload_len_le`
  - `DashboardSnapshotV1` 的总字节数
- `crc32_le`
  - 整个 payload 的 CRC32

#### Data 帧

`0x0079` 请求体：

```text
[payload_chunk...]
```

沿用现有按 chunk 发送、每 chunk 等 ACK 的模式即可，不需要再为这套结构化数据单独造复杂窗口协议。

#### Commit 帧

`0x007A` 请求体：

```text
[refresh_mode:1]
```

字段定义：

- `0`
  - `FULL`
- `1`
  - `FAST`

#### DashboardSnapshotV1

建议使用下面这份固定结构：

```text
offset  size  field
0       1     schema_version
1       1     row_count
2       1     glm_5h_percent
3       1     glm_week_percent
4       1     gpt_5h_percent
5       1     gpt_week_percent
6       1     glm_level_len
7       1     reserved
8       4     total_tokens_u32
12      4     input_tokens_u32
16      4     output_tokens_u32
20      4     cache_tokens_u32
24      5     last_refresh_ascii      // "09:24"
29      5     glm_5h_label_ascii      // "22:17"
34      5     glm_week_label_ascii    // "05-31"
39      5     gpt_5h_label_ascii      // "14:07"
44      5     gpt_week_label_ascii    // "05-31"
49      8     glm_level_ascii         // "PRO", "PLUS"
57      4*33  model rows
189     3     reserved
```

其中每条 `model row` 固定 `33` 字节：

```text
offset  size  field
0       24    model_ascii
24      1     provider_code
25      2     calls_u16
27      4     total_tokens_u32
31      2     share_bp_u16
```

字段规则：

- `model_ascii`
  - 最长 `24` 字节
  - 不足补 `0`
  - 仅允许 ASCII；主机侧遇到非 ASCII 模型名时先裁剪或转别名
- `provider_code`
  - `1=zhipu`
  - `2=openai`
  - `3=anthropic`
  - `4=google`
  - `255=other`
- `share_bp_u16`
  - 百分比基点值，`100.00% = 10000`

这份结构的好处是：

- Host 端非常容易编码
- 固件端可以按固定 offset 直接读字段
- 总大小固定，BLE 下一到两帧就能发完

### 为什么固定中文标签不从主机发送

当前固件里已有的是 Boot Screen 用的小型 ASCII 字模，适合数字、英文和短文本，但并没有现成的通用中文字体系统。

因此新方案建议：

1. 固定中文标签直接固化在设备端
2. 动态文本只传数字、ASCII 时间、ASCII 模型名
3. 固件只补一小套“看板固定标签位图”资产，不做通用中文字库

需要固化到设备端的固定文案只有这类少量标签：

- `今日总量TOKEN`
- `输入`
- `输出`
- `缓存`
- `5小时`
- `一周`
- `上次刷新`
- `GLM CodingPlan`
- `GPT Plus`
- `占比`
- `调用`

这比上完整中文字库轻得多，也更符合经典 ESP32 的资源边界。

### 固件侧渲染规则

建议设备端不要做通用排版，只做固定模板绘制。

#### 固定模板内容

设备端模板与当前页面保持一致：

1. 顶部概览框
2. 左右两个套餐卡片
3. 底部模型表格
4. 左下角 `上次刷新`
5. 右上角本机 `Wi-Fi / battery`

#### 动态数据来源

Host 发送：

- 总量、输入、输出、缓存
- GLM/GPT 百分比
- GLM/GPT 时间标签
- GLM 套餐等级
- Top4 模型列表

设备本地读取：

- `wifiConnected`
- `batteryPercent`

这样可以少一次 Host 的 `READ_MSD` 往返，同时保证显示的是刷新当下的设备状态。

#### 颜色规则

保持和当前位图模式一致：

- 黑色：正文、边框、分隔线、普通进度条、表格进度条
- 红色：套餐卡片中 `percent >= 80` 的填充和百分比文本

#### 文本规则

建议动态文本只支持这三类：

1. 数字
2. 英文大写/小写
3. 常用符号
   - `:`
   - `-`
   - `%`
   - `.`

这能明显降低设备端字模工作量。

### 相关优化点

新增固件端渲染后，可以顺手把下面这些慢点一起消掉：

#### 1. 不再传 30KB 位图

这是最大收益点。

- 位图模式：约 `30KB`
- 固件渲染模式：约 `192B`

BLE 传输耗时会从 `40s` 量级直接降到 `<1s` 量级。

#### 2. 不再做 `rgb_to_bitplanes()`

主机端不再需要：

- PIL 整页渲染
- RGB 到双平面转换
- 保存调试 PNG

这能把主机侧一次刷新链路再缩短一截。

#### 3. 不再读取设备状态再绘图

设备状态改为设备本地绘制后，Host 可以直接跳过当前的 `READ_MSD` 步骤。

#### 4. 无变化跳过更容易做

结构化 payload 很小，Host 可以先比较 `DashboardSnapshotV1` 的二进制内容：

- 相同则整轮跳过
- 不同才发 BLE

这比比较整张位图更稳定，因为不会再被 footer 时间文本影响。

#### 5. 后续更容易做局部逻辑更新

先做整屏固定模板渲染，后面如果确认需要进一步提速，再在固件内做“只重绘部分区域”的内部优化会更自然。

这里注意，是“固件内部按区域重绘并最终整屏刷新”，不是当前就上协议级局部刷新。

### 我的建议

#### 建议 1：位图模式继续保留，但默认先把固件渲染作为实验模式接入

Host 侧加一个显式配置，例如：

```text
TOKEN_DASHBOARD_RENDER_MODE=bitmap|firmware_render
```

这样可以做到：

- 现网继续稳定走位图模式
- 新模式单独验证
- 出问题时不需要回滚协议和业务逻辑，只切配置

#### 建议 2：第一版不要追求“完全复刻 PIL 效果”

第一版固件渲染只需要保证：

- 信息完整
- 对齐稳定
- 红色告警正确
- 表格可读

不要在第一版就追求圆角、虚线细节、完全一致字号。

#### 建议 3：第一版动态文本只支持 ASCII

这是我最明确的建议。

因为当前看板里的动态内容本身就几乎全是数字、英文模型名和时间，没必要为了极少数情况把设备端升级成完整中文排版器。

#### 建议 4：第一版协议直接用固定结构，不要上 TLV

TLV 的灵活性确实更强，但这次需求字段非常固定。

固定结构更适合现在这个项目：

- 固件实现更短
- Host 编码更直接
- 调试抓包更容易
- BLE payload 更紧凑

#### 建议 5：刷新仍然先走 FULL

虽然协议可以预留 `FAST`，但三色屏的观感风险更高。第一版先统一 `FULL`，等实机确认稳定后再考虑按场景放开 `FAST`。

### 预期收益

如果确认并实现这套方案，实际收益会是：

1. 保留原有位图模式，不破坏已有能力
2. 新增结构化 BLE 渲染模式
3. 把传输耗时从 `40s` 量级压到 `<1s`
4. 把总耗时压缩到“主要只剩物理刷新时间”

也就是说，最终瓶颈会从“BLE 传输慢”变成“电子墨水屏本身刷新慢”。
