# Token 看板推送主机开发指南

本文档描述如何开发一个 **BLE 推送主机程序**，配合 J-Calendar 墨水屏固件（`firmware_render` 模式）使用。主机负责采集数据、编码为固件可识别的二进制报文，并通过 BLE 推送到设备完成屏幕刷新。

> 本文只描述协议与数据格式，不依赖任何特定语言或参考实现。任意支持 BLE GATT 的语言/平台均可实现。

---

## 1. 总体架构

```
+------------------+        BLE GATT         +-------------------+
|   推送主机程序    | <---------------------> |  ESP32 墨水屏固件   |
|  (PC / 服务器)    |   单 Characteristic     |  (J-Calendar)     |
+------------------+   读写 + Notify          +-------------------+
        |
        | 采集数据 (HTTP API / 本地文件 / 自定义)
        v
   各类用量数据源
```

工作流程：

1. 主机后台周期性采集数据，生成一份「看板快照」。
2. 设备每隔固定周期（约 5 分钟）从深睡眠唤醒，发出 BLE 广播。
3. 主机扫描到广播后连接设备，读取设备状态。
4. 比对数据是否变化：
   - 无变化 → 发送「无变化休眠」指令，设备立即回睡。
   - 有变化 → 编码快照为 192 字节二进制，分块推送，提交刷新。
5. 设备渲染屏幕后回睡，主机断开连接，等待下一个唤醒窗口。

---

## 2. BLE 连接参数

| 项目 | 值 |
|------|-----|
| Service UUID | `00002446-0000-1000-8000-00805f9b34fb` |
| Characteristic UUID | `00002446-0000-1000-8000-00805f9b34fb` |
| 设备名前缀 | `OD`（按名称前缀过滤扫描结果） |
| MTU | 512 |
| 单块数据上限 | 500 字节（MTU - 操作码 - 余量） |

通信方式：

- 主机 → 设备：对 Characteristic 执行 **Write Without Response**。
- 设备 → 主机：通过 **Notify** 返回响应。
- 每条命令均为「写一条 → 等一条 Notify」的同步请求/响应模型。

---

## 3. 报文通用格式

所有命令首 2 字节为 **操作码（big-endian）**，其后为载荷：

```
[ opcode_hi ][ opcode_lo ][ payload... ]
```

响应同样以 2 字节操作码开头，`response[0]` 恒为 `0x00`，`response[1]` 标识结果。

### 命令操作码表

| 操作码 | 名称 | 方向 | 说明 |
|--------|------|------|------|
| `0x0044` | READ_MSD | 主机→设备 | 读取设备状态（电量、刷新标志等） |
| `0x0078` | DASHBOARD_RENDER_START | 主机→设备 | 开始一次看板推送，声明长度与 CRC |
| `0x0079` | DASHBOARD_RENDER_DATA | 主机→设备 | 推送一块载荷数据 |
| `0x007A` | DASHBOARD_RENDER_COMMIT | 主机→设备 | 提交并触发刷新 |
| `0x007D` | DASHBOARD_NO_CHANGE_SLEEP | 主机→设备 | 数据无变化，通知设备休眠 |

### 错误码（COMMIT/数据校验失败时返回）

| 错误码 | 含义 |
|--------|------|
| `0x01` | 协议版本不支持 |
| `0x02` | 载荷长度非法 |
| `0x04` | CRC 校验不匹配 |
| `0x05` | 状态机错误（命令顺序不对） |
| `0x07` | 设备忙 |
| `0x08` | 刷新模式不支持 |

## 4. 设备状态读取（READ_MSD）

连接后先读取设备状态，用于判断电量、是否需要全刷。

**请求**：`00 44`

**响应**：以 `00` 开头，载荷从偏移 2 开始（MSD payload）。关键字段：

| 字节偏移（在响应中） | 含义 |
|---------------------|------|
| `resp[2..17]` | MSD payload（16 字节） |
| MSD byte 14 | 电压低字节（单位 10mV） |
| MSD byte 15 bit0 | 电压高位 |
| MSD byte 15 bit3 (`0x08`) | 局刷基线就绪标志 `partial_baseline_ready` |
| `resp[18]` bit0 (`0x01`) | 强制全刷标志 `force_full_refresh` |

**电压换算**：

```
voltage_raw = ((msd[15] & 0x01) << 8) | msd[14]
voltage_mv  = voltage_raw * 10
```

**电量百分比**（线性映射，可按需调整）：

```
满电压 = 4.20 V  -> 100%
空电压 = 3.30 V  ->   0%
percent = clamp((voltage - 3.30) / (4.20 - 3.30) * 100, 0, 100)
```

---

## 5. 刷新模式选择

| 模式 | 值 | 何时使用 |
|------|----|---------|
| FULL（全刷） | `0` | `force_full_refresh=1` 或 `partial_baseline_ready=0` |
| FAST（快刷） | `1` | 局刷基线已就绪且无需强制全刷 |

逻辑：

```
if force_full_refresh or not partial_baseline_ready:
    mode = FULL
else:
    mode = FAST
```

## 6. 看板推送流程（核心）

完整流程为 **START → DATA(分块) → COMMIT → 等待刷新结果**。

### 6.1 START — `0x0078`

声明本次推送的版本、长度与校验。

**请求载荷**（操作码后接 8 字节，**小端**）：

```
[00][78][ version:u8 ][ flags:u8 ][ payload_len:u16-LE ][ crc32:u32-LE ]
```

| 字段 | 类型 | 值 |
|------|------|-----|
| version | u8 | `1` |
| flags | u8 | `0` |
| payload_len | u16 LE | `192` |
| crc32 | u32 LE | 对完整 192 字节载荷计算的 CRC32 |

**成功响应**：`resp[0]==0x00 && resp[1]==0x78`

### 6.2 DATA — `0x0079`

把 192 字节载荷按 ≤500 字节分块发送（实际一块即可发完）。

**请求**：`00 79` + 数据块

**成功响应**：`resp[0]==0x00 && resp[1]==0x79`，逐块发送直到全部发完。

### 6.3 COMMIT — `0x007A`

提交并触发屏幕刷新。设备先回 ACK，再阻塞渲染（约 15 秒），需设置较长超时（建议 120s）。

**请求**：`00 7A` + `[refresh_mode:u8]`（`0`=FULL，`1`=FAST）

**ACK 响应**：`resp[0]==0x00 && resp[1]==0x7A`

**刷新结果 Notify**（COMMIT 之后再等一条，建议超时 65s）：

| `resp[1]` | 含义 |
|-----------|------|
| `0x7B` | 刷新成功 |
| `0x7C` | 刷新超时/失败 |

### 6.4 时序图

```
主机                          设备
 | --- 00 78 (START) -------> |
 | <-- 00 78 (ACK) ---------- |
 | --- 00 79 (DATA) -------> |
 | <-- 00 79 (ACK) ---------- |
 |        ...分块...          |
 | --- 00 7A (COMMIT) -----> |
 | <-- 00 7A (ACK) ---------- |
 |        (设备渲染中)        |
 | <-- 00 7B (刷新成功) ----- |
```

## 7. 无变化休眠（NO_CHANGE_SLEEP）

当本轮采集数据与上次推送的内容一致时，不必重刷屏幕，发送此命令让设备立即回睡，并同步当前时间。

**请求**：`00 7D` + `[hour:u8][minute:u8][second:u8]`（当前本地时间）

**成功响应**：`resp[0]==0x00 && resp[1]==0x7D`

> 建议主机维护一份「上次成功推送内容的哈希」，与本轮快照哈希比较。一致则走此分支，否则走推送流程。

## 8. 看板二进制载荷格式（DashboardSnapshotV1）

**固定 192 字节**，所有多字节整数均为 **小端（little-endian）**，字符串为 ASCII、定长、不足补 `0x00`。

### 8.1 整体布局

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 1 | schema_version | u8 | 固定 `1` |
| 1 | 1 | row_count | u8 | 模型行数（0–4） |
| 2 | 1 | glm_5h_percent | u8 | GLM 5 小时用量百分比 0–100 |
| 3 | 1 | glm_week_percent | u8 | GLM 周用量百分比 0–100 |
| 4 | 1 | gpt_5h_percent | u8 | GPT 5 小时用量百分比 0–100 |
| 5 | 1 | gpt_week_percent | u8 | GPT 周用量百分比 0–100 |
| 6 | 1 | glm_level_len | u8 | GLM 等级字符串长度（≤8） |
| 7 | 1 | reserved | u8 | 保留，填 `0` |
| 8 | 4 | total_tokens | u32 LE | 今日总 token |
| 12 | 4 | input_tokens | u32 LE | 输入 token |
| 16 | 4 | output_tokens | u32 LE | 输出 token |
| 20 | 4 | cache_tokens | u32 LE | 缓存读取 token |
| 24 | 5 | last_refresh_label | ASCII | 最近刷新时间 `HH:mm` |
| 29 | 5 | glm_5h_label | ASCII | GLM 5h 重置时间 `HH:mm` |
| 34 | 5 | glm_week_label | ASCII | GLM 周重置 `MM-DD` |
| 39 | 5 | gpt_5h_label | ASCII | GPT 5h 重置时间 `HH:mm` |
| 44 | 5 | gpt_week_label | ASCII | GPT 周重置 `MM-DD` |
| 49 | 8 | glm_level | ASCII | GLM 套餐等级（如 `PRO`），右侧补 0 |
| 57 | 132 | models[4] | 见下 | 4 个模型行，每行 33 字节 |
| 189 | 1 | sync_hour | u8 | 同步时刻 时 |
| 190 | 1 | sync_minute | u8 | 同步时刻 分 |
| 191 | 1 | sync_second | u8 | 同步时刻 秒 |

> 时间标签字段长 5 字节，`HH:mm`（如 `09:30`）正好 5 字符；`MM-DD`（如 `6-17`）不足 5 字符时右侧补 `0x00`。

### 8.2 模型行格式（每行 33 字节）

偏移相对于该行起始（第 1 行从全局偏移 57 开始）：

| 行内偏移 | 大小 | 字段 | 类型 | 说明 |
|---------|------|------|------|------|
| 0 | 24 | model | ASCII | 模型名，定长，不足补 0 |
| 24 | 1 | provider_code | u8 | 厂商代码（见下表） |
| 25 | 2 | calls | u16 LE | 调用次数，上限 65535 |
| 27 | 4 | total_tokens | u32 LE | 该模型 token 总量 |
| 31 | 2 | share_bp | u16 LE | 占比，基点（0–10000，即 0–100.00%） |

未使用的模型行整行填 `0x00`。

### 8.3 厂商代码（provider_code）

| 代码 | 厂商 |
|------|------|
| 1 | zhipu（智谱） |
| 2 | openai |
| 3 | anthropic |
| 4 | google |
| 255 | 其他/未知 |

### 8.4 模型名处理建议

- 仅保留 ASCII 字符，非 ASCII 一律替换为 `_`。
- 可去掉冗长前缀（如 `claude-`）以适配屏幕显示宽度。
- 截断到 24 字节以内。

### 8.5 占比换算

```
share_bp = clamp(round(share_percent * 100), 0, 10000)
# 例：43.2% -> 4320
```

## 9. CRC32 计算

对**完整的 192 字节载荷**计算标准 CRC32（zlib/IEEE 802.3 多项式，与大多数语言标准库一致），取 32 位无符号值，按小端写入 START 命令。

```
crc32 = CRC32(payload) & 0xFFFFFFFF
```

设备端会重新计算并比对，不匹配返回错误码 `0x04`。

---

## 10. 主机调度建议

固件唤醒周期约 5 分钟，主机需在每个唤醒窗口内尽快完成连接与推送，避免设备久等耗电。建议：

- **后台采集**：独立循环（如每 30 秒）采集数据并缓存，BLE 窗口内直接复用缓存，不在连接期间等待外部接口。
- **窗口对齐**：推送完成后，计算到下一个 5 分钟唤醒窗口的等待时间再开始下一轮扫描，期间暂停扫描省资源。
- **扫描超时**：单次扫描 5 秒左右，未发现广播则视为本窗口设备未唤醒，静默跳过。
- **去重推送**：维护上次成功推送内容的哈希；数据未变只发 NO_CHANGE_SLEEP。
- **失败不落盘**：只有推送成功才更新「已同步哈希」，避免漏刷。

## 11. 数据采集（数据源自定义）

载荷字段的数据来源完全由主机自定义，可来自任意 HTTP API、本地日志或数据库。需要产出的字段：

- 今日 token 统计：total / input / output / cache。
- 各 AI 套餐的 5 小时窗口与周窗口用量百分比及重置时间标签。
- Top 模型列表（最多 4 个）：模型名、厂商、调用次数、token 总量、占比。

> 采集逻辑与本协议解耦。你只需把采集结果填入第 8 节的字段并编码即可。

## 12. 实现自测清单

- [ ] 能按名称前缀 `OD` 扫描并连接设备。
- [ ] 能订阅 Notify 并正确接收响应。
- [ ] READ_MSD 解析电量、`partial_baseline_ready`、`force_full_refresh` 正确。
- [ ] 载荷恒为 192 字节，字段偏移与字节序与第 8 节一致。
- [ ] CRC32 与设备端一致（START 不返回 `0x04`）。
- [ ] START/DATA/COMMIT 顺序正确，COMMIT 后能收到 `0x7B`。
- [ ] 数据无变化时走 NO_CHANGE_SLEEP，收到 `0x7D`。
- [ ] 刷新模式按设备状态正确选择 FULL/FAST。
- [ ] 推送成功后才更新本地「已同步」状态。
